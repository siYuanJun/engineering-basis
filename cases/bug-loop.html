CASE / 判定口径

缺陷闭环，改完算不算完

bug-loop 把接单、定位、修复、反馈、关闭拆成六个阶段，每个阶段有明确的落地条件。下面三个样例走同一套闸门判定，可以直接跑出同样的结果。

公开切片 ｜ 零依赖 ｜ 样例输出为 2026-11-24 本地实跑

01它解决什么

缺陷处理最含糊的是收口。代码改完不等于单能结；归因是代码问题还是需求问题，处理方式完全不同；关闭权限不在开发手里。没有固定的落地条件，就会出现“改完了但不敢关”“关了又被激活”“需求问题用代码绕过”。

  • 归因先定性：代码类还是需求类，决定谁能落
  • 需求类归因一律人拍板，AI 不替产品做决定
  • 改动按重量分档，涉及表结构与数据迁移由人主导
  • 关闭动作交给提报人，AI 只提醒

02三个可复现的判定

样例 A · 代码问题，自测通过RESOLVE
python3 demos/bug-loop/bug_gate.py demos/bug-loop/fixtures/resolve.json
{ "verdict": "RESOLVE", "reason": "代码类归因且自测通过，可写回解决" } exit 0

归因 fixed，自测通过，改动属于 L1 可直接撤回。这类可以自动写回解决，并留下复现步骤与验证方式。

样例 B · 归到需求问题HOLD_OWNER
python3 demos/bug-loop/bug_gate.py demos/bug-loop/fixtures/need-decision.json
{ "verdict": "HOLD_OWNER", "reason": "归因为 bydesign，属于需求判断，需人拍板" } exit 3

bydesign 意味着“不是缺陷，是设计如此”。这类判断不能由开发自己下，否则需求边界会被代码悄悄改写。停下来，等人拍板。

样例 C · 关闭这张单HANDOFF
python3 demos/bug-loop/bug_gate.py demos/bug-loop/fixtures/close.json
{ "verdict": "HANDOFF", "reason": "关闭只由提报人操作，AI 提醒到位即止" } exit 3

就算提报人已经口头确认，关闭动作也由他在页面上点。AI 把备注、截图、复现步骤备齐，然后交接，不代点。

03规则是脚本拦截

“需求类归因要人拍板”写在规范里，执行时最容易被跳过，因为开发觉得自己判断得准。这里把归因取值直接写进判定，值不对就落不下去。

动作条件结果
resolve归因为需求类（tostory / bydesign / notrepro / postponed / willnotfix）停下，等人拍板
resolve归因为代码类，但自测未通过停下，不写回解决
resolve改动涉及表结构、数据迁移、存量修数停下，由人主导评估
close任何情况交接给提报人

04判据与边界

维度口径
判什么这条单的当前动作能不能由 AI 落地
什么时候可落代码类归因、自测通过、改动可直接撤回
什么时候停手需求类归因、改动不可撤回、关闭动作、争议与超时
谁拍板需求归因与关闭由人或提报人；合并共享分支按授权级别
职责范围读单、定位、归因、修复、写状态、对账；关闭与打回由人操作

执行方式：本地运行，Python 3 直接跑；输入为一条缺陷单的 JSON；退出码 0 = 可落，3 = 需人拍板或交接，1 = 输入不合法。

05怎么复现

git clone --depth 1 https://github.com/siYuanJun/engineering-basis cd engineering-basis for f in resolve need-decision close; do python3 demos/bug-loop/bug_gate.py demos/bug-loop/fixtures/$f.json echo "exit=$?" done

三个样例为构造输入，分别覆盖可落、需人拍板、交接三种结果。
